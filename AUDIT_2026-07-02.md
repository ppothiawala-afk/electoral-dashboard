# Electoral Dashboard — Full Project Audit
**Date:** July 2, 2026 · **Auditor:** Claude (Fable 5) · **Status:** For review — nothing built or changed

---

## 1. System as designed

The pipeline has four layers:

1. **Claude scheduled task** (`electoral-dashboard-updater`, Mondays 1:08 PM PT, jitter up to ~8 min) — researches membership changes and rating moves, writes `constants_patch.json`, `weekly_briefing_YYYY-MM-DD.md`, and appends to `history.json`.
2. **Local Mac cron** (Mondays 1:00 PM PT via `run_weekly_update.sh`) — runs `update_sheet.py` (scrapes Wikipedia/Ballotpedia/Press Gallery, writes ratings + chamber balance to the Sheet) then `apply_constants_patch.py` (applies Claude's patch, archives it).
3. **Google Sheet** (ID `1THi4…IqA`) — five tabs (Senate, House, Governors, StateLeg, Constants), published as CSV.
4. **GitHub Pages dashboard** (`index.html` reads published CSVs live; `history.html` reads a co-located `history.json`).

The design itself is sound: Claude never writes to the Sheet directly (Drive MCP is read-only), all writes flow through the audited patch mechanism. The problems are in execution, sequencing, and consistency.

## 2. Critical findings

### 2.1 The local cron is almost certainly not running (SEV-1)
`update_log.txt` contains exactly **one run ever: June 2, 1:49 PM** (a Tuesday, mid-afternoon — almost certainly a manual invocation, not cron). Evidence stack:

- The **June 29 `constants_patch.json` is still sitting unapplied** three days later. A working Monday cron would have consumed and archived it.
- The only applied-patch archive (`constants_patch.applied_2026-06-15.json`) coincides with `fix_2026_06_15_murkowski.py` and a same-minute mtime on `apply_constants_patch.py` — that patch was applied **manually in a Claude session**, not by cron.
- Likely root cause: **macOS TCC blocks `cron` from reading `~/Documents`** unless `cron` has been granted Full Disk Access. The script would fail silently before it can even write its own log (the log lives inside `~/Documents` too — a design flaw: failures are invisible). A sleeping Mac also skips cron jobs entirely; `launchd` runs missed jobs on wake, `cron` does not.

**Net effect:** the "automated" Sheet-update layer has effectively never run on schedule. All real updates have been Claude sessions doing manual pushes.

### 2.2 Sequencing flaw: the patch always misses its own cron (SEV-1)
Even if cron worked: cron fires at **1:00 PM**, Claude's task fires at **1:08 PM + jitter** and finishes writing the patch ~1:20 PM. Every patch is therefore applied **seven days stale** — e.g., `LAST_UPDATED: 2026-06-29` would be written to the Sheet on July 6. The skill text claims the patch "is applied automatically by the Monday 1pm cron," which is true only for *last* week's patch. The two schedules were never sequenced.

### 2.3 The local folder is not a git repo (SEV-2)
You described the project as "a repo on GitHub," but there is **no `.git` directory** in the project folder. Whatever deploys `index.html`, `history.html`, and `history.json` to `ppothiawala-afk.github.io/electoral-dashboard/` is a manual, undocumented step. Consequences:

- `history.html` reads `history.json` from its own directory — if `history.json` isn't re-pushed after each weekly append, the public archive page silently lags.
- No version history for `index.html` (93 KB, hand-edited), the Python scripts, or the skill.
- **Security:** `service_account.json` (live private key for `electoral-updater@electoral-dashboard-497521…`) sits in this same folder. The moment this folder is pushed to GitHub as-is, the key is public and the Sheet is writable by anyone. There is no `.gitignore` to prevent it.

### 2.4 Three divergent skill documents; the scheduled task runs the worst one (SEV-2)
| File | Version | Problem |
|---|---|---|
| `~/Documents/Claude/Scheduled/electoral-dashboard-updater/SKILL.md` | **Old** — this is what actually runs Mondays | Instructs Claude to "update those cells in the Constants tab" via Drive MCP — **direct sheet writes, which the MCP can't do and which contradicts the patch mechanism**. No `constants_patch.json`, no `history.json`, no citation rules. |
| `SKILL_updated.md` (repo root) | Identical copy of the old version | Misleading name; it's not updated. |
| `skills/electoral-dashboard-updater/SKILL.md` | **New, correct** — patch-based 7-step flow, citation format, key_cols gotcha, history append | Not connected to the scheduled task. |

So the weekly consistency you're after currently depends on the running model *ignoring its instructions* and doing the right thing from context. That's exactly the inconsistency generator you suspected.

### 2.5 Data-model inconsistency: Senate independents (SEV-2)
- House constants are **exclusive**: 218 R + 212 D + 1 I + 4 V = 435 ✓ (validated everywhere).
- Senate constants are **overlapping**: 53 R + 47 D + 3 I = 103. The 3 independents (Sanders, King, Murkowski) are evidently counted *inside* the R/D caucus figures. No skill, script, or eval documents this, and **no validation rule exists for the Senate at all** (nothing checks the total is 100). Any future model reading "SENATE_D: 47, SENATE_I: 3" will reasonably conclude the counts should sum to 100 and "fix" them — a guaranteed future error.

### 2.6 Pipeline execution gaps from the last run (SEV-3)
- `history.json` has weeks 5/26 → 6/22 but **no 6/29 entry**, despite `weekly_briefing_2026-06-29.md` existing and `generated: 2026-06-29`. Step 7 was skipped or failed silently on the last run.
- The June 2 run (old script version) wrote **HOUSE_VACANCIES 5 → 0** to the live Sheet from a stale Press Gallery page. The vacancy-floor guard was added to `update_sheet.py` *after* that run (file mtime 2:43 PM vs. run at 1:49 PM) — and **the fixed scraper has never executed in production since**. The current Wikipedia-HTML scraping path is unproven; the logged run found 0 ratings across all four scrape targets.

## 3. Code-fidelity review

### `update_sheet.py` (1,024 lines)
Generally well-commented and defensive, but:

- **Dead code:** `fetch_wiki_wikitext()` and `extract_ratings_from_wikitext()` (~150 lines) are never called; the docstring still advertises the wikitext approach the code abandoned. Same for Pattern 1–4 regex machinery.
- **Duplicated logic:** the orchestrator re-implements Senate/Governors/House update loops inline instead of calling `update_ratings_in_tab()` — two code paths that must be kept in sync (the inline Senate path filters `Up in 2026 == YES`; the generic path relies on caller-supplied `key_cols`). Drift here caused the Murkowski incident pattern.
- **Fragile scraping:** ratings come from positional column indexes (Cook = col 4) on Wikipedia wikitables with a left-to-right fallback scan across cols 4–7. A column reorder silently switches the forecaster being treated as canonical. Special-election rows ("Ohio (special)") have their parenthetical stripped, colliding with the regular seat's key.
- **Dubious math:** in `scrape_house_balance()`, when the vacancy floor kicks in, R/D/I are **proportionally rescaled and rounded** — inventing seat counts that never existed. Safer: skip the Constants write and flag for review.
- **StateLeg ratings are synthetic:** seat-margin buckets plus a hard-coded DLCC-target nudge. Fine as a heuristic, but the dashboard presents them on the same 7-point scale as forecaster ratings with no provenance distinction.
- Runtime env: user's Mac runs Python 3.9 (EOL — Google libs warn); `run_weekly_update.sh` sources `.zshrc` for env (fragile under cron, which uses `sh` semantics and no login environment) and then overrides with an inline base64 of the key file anyway — the sourcing is vestigial.

### `apply_constants_patch.py`
The strongest file in the repo. The `_check_key_uniqueness()` pre-flight (added after the Murkowski incident) is exactly right. Two gaps: (1) no validation that `updates` satisfies the 435 rule before writing — the skill asks Claude to validate, but the script that touches the Sheet doesn't enforce it; (2) archives the patch even when it applied zero changes or hit warnings, so a failed patch looks identical to a successful one afterward.

### Housekeeping
One-off scripts accumulating at root (`patch_2026_05_26.py`, `fix_2026_06_15_murkowski.py`, `direct_update.py` — which references a differently-named credentials file that no longer exists); a stale LibreOffice lock file from May 13; `Electoral Dashboard Data.xlsx` untouched since May 26 (vestigial — the real store is the Google Sheet); `__pycache__` at root; naming drift (`weekly_update_2026-05-26.md` vs. `weekly_briefing_*`).

## 4. Review of the existing skill + eval (the lower model's work)

**The skill** (`skills/electoral-dashboard-updater/SKILL.md`) is genuinely good: correct patch-based flow, the two-rows-per-state gotcha, inline-citation discipline, the Kiley edge case, history append. Weaknesses:

1. It was never wired into the scheduled task (§2.4) — the single biggest fidelity gap in the whole project.
2. No **idempotency/pre-flight**: it never says "check whether last week's patch was actually applied before overwriting `constants_patch.json`." Had it, the dead cron would have been caught on June 22 instead of by this audit.
3. No Senate validation rule and no documentation of the overlapping-I semantics (§2.5).
4. Step 7 (history append) has no verification step — and it was indeed silently skipped on 6/29.
5. It embeds a full patch example with **concrete current values** (218/212/1/4), which future runs may anchor on instead of the Sheet's live values.

**The eval** (`trigger_evals.json`, 10 positive / 10 negative) is a *trigger-only* eval — it tests whether the skill fires, not whether the run is any good. The negatives are well-chosen hard cases. But for your stated goal ("consistency for the weekly pull/summary") it tests the wrong thing entirely: nothing checks patch schema validity, the 435 invariant, key_cols safety, citation format, briefing structure, or the history append. Two labels are also debatable: "did any senators switch parties recently?" and "who won the georgia 14 special election?" are marked *no-trigger*, yet both are literally Step 1 work.

## 5. My proposed skill + eval (design only)

### 5.1 One canonical skill, three enforced contracts
Replace all three documents with a single `SKILL.md` (repo `skills/` dir, symlinked/copied into the scheduled task) structured around contracts rather than a narrative:

- **Pre-flight contract (new):** verify last week's patch was consumed (`constants_patch.applied_*` exists for last Monday; `constants_patch.json` absent). If not → lead the briefing with a ⚠️ PIPELINE ALERT and do not silently overwrite. Also verify `history.json`'s last entry matches last week's briefing.
- **Data contract:** exact JSON Schema for `constants_patch.json` and the `history.json` entry; invariants stated once: `HOUSE_R+D+I+V = 435`; `SENATE_R+D = 100` with `SENATE_I ⊆ caucus counts` (overlap semantics documented explicitly); ratings ∈ 7-point enum; Senate/Governors changes must use compound keys (`["State","Up in 2026"]`); dates ISO. Placeholder values in examples (`<int>`), never live numbers.
- **Output contract:** briefing template with required sections and the inline-citation rule; every rating shift must carry forecaster + date + URL; every chamber claim sourced to Clerk/Press Gallery.
- **Post-flight contract (new):** run a small `validate_patch.py` (to be built) that machine-checks schema + invariants + key uniqueness against a cached copy of the Sheet before finishing; confirm history entry appended by re-reading the file.

### 5.2 Two-layer eval
**Layer 1 — trigger eval:** keep the existing 20 cases, fix the two mislabeled negatives, add 4 cases around the pipeline-alert path ("did last week's patch get applied?", "why is the sheet stale?").

**Layer 2 — output eval (the part that actually buys consistency):** fixture-based, machine-checkable, no LLM judge needed for most of it. Given a frozen fixture (mock sheet CSV + mock "research findings" doc), a passing run must produce:

| Check | Type |
|---|---|
| Patch parses, matches JSON Schema | deterministic |
| 435 / Senate invariants hold | deterministic |
| Every Senate/Governors change uses compound key; key matches exactly 1 fixture row | deterministic |
| Briefing contains all required sections; every rating-shift line has an inline `[…](url)` citation | deterministic (regex) |
| `history.json` gains exactly one valid entry, prior entries untouched | deterministic |
| Re-running on the same fixture is a no-op / raises the pipeline alert | deterministic |
| Narrative accuracy vs. fixture facts (no invented moves, correct old→new ratings) | small rubric, LLM-graded |

Fixtures would include the known failure modes as regression cases: the Murkowski two-row trap, the stale-Press-Gallery vacancy trap, the Senate-sums-to-103 trap, and the unapplied-patch trap.

## 6. Weekly execution without a Claude scheduled task

Root problem to solve: the Mac is an unreliable host (TCC, sleep, cron's silent failures), and Claude's scheduled task requires the desktop app to fire. Since the project already lives on GitHub, the natural answer is:

### Recommended: GitHub Actions cron (deterministic layer), API-driven research (intelligence layer)
1. **Make the folder an actual git repo** (with `.gitignore` covering `service_account.json`, `*.xlsx`, `__pycache__`, lock files) pushed to the existing GitHub repo that serves Pages.
2. **Deterministic weekly job — GitHub Actions** `schedule: cron('0 20 * * 1')` (Mon 1 PM PT): runs `update_sheet.py` + `apply_constants_patch.py` with the service-account key stored as a **GitHub Actions secret** (`GOOGLE_CREDENTIALS`, already supported by the code — the env-var path exists). The job commits the archived patch + updated `history.json`, which auto-redeploys Pages. Runs whether or not your Mac is on; logs are visible in the Actions tab; failures email you.
3. **Research/briefing layer — two options:**
   - **3a (fully autonomous):** a second Actions job calls the **Anthropic API** (a script using Claude with the web-search tool) to do Steps 1–7, writing the patch and briefing, then the deterministic job applies it. No Claude app involved anywhere; needs an `ANTHROPIC_API_KEY` secret and modest per-run cost.
   - **3b (human-in-the-loop, zero new infra):** you kick off the briefing in Cowork whenever you like (skill triggers on request); the Actions cron applies whatever patch has been committed. Claude is no longer load-bearing for the *schedule* — only for the research, run at your convenience.
4. **Sequencing fix comes free:** research job at Mon 9 AM, apply job at Mon 1 PM — patch applied same day, not 7 days later.

**Alternatives considered:** `launchd` on the Mac (fixes sleep/missed-run issues and is the minimal patch to the status quo, but still single-machine and still needs Full Disk Access); a $4/mo VPS or Cloud Run + Cloud Scheduler (works, but strictly more infra than Actions for zero benefit here). Not recommended over Actions.
